# 项目需求分析

> 依据：v2.0 第一、二章。

## 1. 项目背景

随着 LLM 与 AI Agent 技术普及，Agent 架构的系统越来越复杂，开发者普遍面临 7 类问题：

1. 执行过程不透明，难以理解内部决策；
2. 多次 LLM / 工具调用之间的关系难以追踪；
3. 执行失败后难以快速定位根因；
4. Token 与模型调用成本难以分析；
5. 出现重复调用、无限循环、规划不合理等问题；
6. 历史故障经验无法复用；
7. 缺乏对 Agent 执行效果的系统性评估。

传统可观测性平台只负责「采集 + 展示 + 统计」，最终仍需人肉分析。**AgentTrace 的差异化在于：用 AI 自主完成分析、定位、给出带证据的优化建议**。

## 2. 项目定位

- **名称**：AgentTrace
- **一句话**：基于 Multi-Agent 的 AI Agent 自主诊断与优化平台。
- **英文**：An Autonomous AI Agent Observability and Diagnosis Platform.
- **核心理念**：让 AI Agent 不仅「观察」另一个 Agent，还能「理解、诊断、并帮助它变得更好」。

## 3. 核心目标（能力清单）

1. Agent 执行数据采集
2. Trace / Span 链路追踪
3. Agent 自主任务规划（Planning）
4. Multi-Agent 协同诊断
5. RAG 故障知识检索
6. Memory 历史经验管理
7. Tool Calling 外部工具调用
8. Reflection 诊断结果反思
9. Agent Evaluation 效果评估
10. 自动生成诊断报告
11. MCP 工具服务开放

## 4. 核心用户

- AI Agent 开发者
- LangGraph / LangChain 开发者
- Python 后端开发者
- AI 应用开发团队

## 5. 核心业务场景（必须围绕真实场景开发）

### 场景一：执行链路分析
用户：「帮我分析一下这次 Agent 执行过程。」→ 查 Trace → 拉 Span 列表 → 分析步骤 → 识别慢节点 → 检测重复工具调用 → 总结并出报告。

### 场景二：故障诊断
用户：「为什么我的 Agent 最近经常执行失败？」→ 理解目标 → 制定计划 → 查异常 Trace → 分析错误类型与位置 → RAG 检索历史故障 → 对比相似案例 → 根因分析 → 给建议。

### 场景三：成本分析
用户：「为什么最近执行成本增加了 30%？」→ 查时间范围记录 → 统计 Token → 对比模型调用次数 → 分析输入/输出 Token → 检查重复调用 → 分析成本变化原因 → 给建议。

### 场景四：历史经验复用
用户：「这次的问题之前遇到过吗？」→ 提取故障特征 → 检索历史诊断记录 → 从长期记忆找相似经历 → 从 RAG 找资料 → 对比 → 给参考方案。

### 场景五：优化建议
用户：「帮我分析这个 Agent 有哪些可以优化的地方。」→ 从执行效率 / 模型调用次数 / Token / 工具调用效率 / 规划合理性 / 异常处理 / 上下文管理 七个角度分析 → 输出结构化报告。

> **约束**：第一阶段只提供优化建议，**禁止未经用户确认就修改外部 Agent 的代码或配置**。

## 6. 功能需求

- **采集**：SDK 上报 Trace / Span / Token 使用（同步 + 异步 + 重试）。
- **查询**：Trace / Span / 错误 / 成本 的查询与筛选。
- **诊断**：基于 Multi-Agent 的自主诊断，输出结构化报告。
- **知识库（RAG）**：文档上传、解析、切分、Embedding、检索，结果可溯源。
- **记忆（Memory）**：工作 / 情景 / 语义 / 程序性记忆的写入、检索、更新、去重、巩固。
- **反思（Reflection）**：证据检查、一致性检查、有限次数重分析。
- **评估（Evaluation）**：标准测试集 + 指标 + 自动化评估报告。
- **MCP**：把诊断能力开放给其他 Agent。
- **Dashboard**：Overview / Trace Explorer / Trace Detail / AI 诊断 / 知识库 / 评估页。

## 7. 非功能需求

- **安全性**：API Key 走环境变量；日志脱敏；SDK 上报鉴权；输入校验；Prompt Injection 防护；权限隔离。
- **可靠性**：限制 Agent 最大执行时间、最大工具调用次数、最大规划步数、反思循环次数；外部修改操作必须 Human-in-the-loop。
- **可扩展性**：模型 / Embedding / 数据库访问均抽象成可插拔接口。
- **可维护性**：模块化单体、职责清晰、ADR 记录架构决策。
- **可测试性**：每个模块带单元/集成测试；RAG / Memory / Evaluation 有量化评估。
- **可部署性**：Docker Compose 一键启动。

## 8. 第一阶段边界（明确「不做」）

- 所有诊断工具**只读**，不删除/修改用户数据；
- **不**自主修改外部 Agent 代码或配置；
- 只实现 Python SDK，LangGraph/LangChain CallbackHandler 后置；
- RAG 仅 Vector Search + Metadata Filtering + Top-K，Hybrid/Reranker/Agentic RAG 后置；
- 先做模块化单体，不拆微服务。

## 9. 需求验收（摘录自 v2.0 第二十二章）

功能验收：能采集真实执行记录、能查 Trace/Span、能完成基础诊断、能动态规划、能多 Agent 协作、能用 RAG、能用长期记忆、能反思、能出结构化报告、能通过 MCP 开放工具。
