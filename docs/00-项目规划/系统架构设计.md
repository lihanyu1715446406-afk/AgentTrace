# 系统架构设计

> 依据：v2.0 第三、四、六章。

## 1. 总体架构：五层

```
┌──────────────────────────────────────────────────────────┐
│ 第五层 展示层：React + TS + AntD + ECharts               │
│   Overview / Trace Explorer / Detail / AI诊断 / KB / Eval │
└──────────────────────────┬───────────────────────────────┘
                           │ REST API
┌──────────────────────────▼───────────────────────────────┐
│ 第四层 服务接口层：FastAPI / REST / MCP Server / Auth /    │
│         异步任务管理                                       │
└──────────────────────────┬───────────────────────────────┘
                           │ 调用
┌──────────────────────────▼───────────────────────────────┐
│ 第三层 Agent 智能层（核心）                                │
│  Orchestrator / Planning / Trace·Error·Cost Analyzer /     │
│  Knowledge Agent / Report Agent / Reflection / Memory Mgr  │
└──────────────────────────┬───────────────────────────────┘
                           │ Tool Calling / Repository
┌──────────────────────────▼───────────────────────────────┐
│ 第二层 数据管理层：Repository / PG / Qdrant / Redis        │
└──────────────────────────┬───────────────────────────────┘
                           │ SDK 上报
┌──────────────────────────▼───────────────────────────────┐
│ 第一层 数据采集层：Python SDK / Trace·Span Collector / 校验 │
└──────────────────────────────────────────────────────────┘
```

分层职责清晰：**上层只依赖下层接口，禁止反向依赖**（例如 Agent 层不得直接 import FastAPI 请求对象）。

## 2. 核心业务流程

```
用户 → FastAPI 接收诊断请求 → Agent Orchestrator → Planning Engine
      → 按任务选分析 Agent → Tool Calling 查 Trace/Span
      → 必要时 RAG / Memory → 初步诊断 → Reflection 检查
      → Report Agent 出报告 → 保存诊断记录 → 返回用户
```

关键认知（v2.0 明确强调）：**Planning / RAG / Memory / Tool Calling 不是五个固定顺序步骤，而是执行过程中按需反复调用的能力**。

## 5. Agent Core 设计概览

采用 **Supervisor + Specialized Agents**（v2.0 第九章）：

- **Supervisor（Orchestrator）**：接收任务 → 生成计划 → 分配 → 控流程 → 汇总。
- **专业 Agent**：Trace Analyzer / Error Analyzer / Cost Analyzer / Knowledge Agent / Report Agent。

### 统一共享状态（AgentState）

用 Pydantic / TypedDict 定义，字段受控共享：

`task_id / project_id / user_query / task_type / execution_plan / current_step / trace_ids / analysis_results / retrieved_documents / retrieved_memories / findings / reflection_result / final_report / errors`

### 三种协作模式

1. **顺序执行**：有依赖时（查异常 → 分析 → 检索 → 报告）。
2. **并行执行**：互相独立时（Trace 分析 / 成本 / 错误统计并行）。
3. **条件路由**：按任务类型选 Agent（成本任务不调 Error Analyzer）。

### Agent 通信规范

统一通过 LangGraph State 传递**结构化结果**，禁止把不受控的自由文本当唯一通信协议。

## 6. 关键架构决策（ADR）

### ADR-0001 模块化单体，不拆微服务
- **决策**：初期单体 + 清晰模块边界。
- **理由**：降低部署与维护成本；等项目规模与团队需求明确后再考虑拆分。

### ADR-0002 Supervisor + Specialized Agents
- **决策**：多 Agent 采用 Supervisor 编排 + 专业子 Agent。
- **理由**：比纯图结构更易控制流程与汇总，利于教学与演进。

### ADR-0003 用 LangGraph 实现 Agent 工作流
- **决策**：核心 Agent 工作流基于 LangGraph（StateGraph + Conditional Edges + Checkpointer）。
- **理由**：原生支持有状态多步工作流、Multi-Agent、持久化与 Human-in-the-loop。

### ADR-0004 第一阶段工具只读
- **决策**：诊断工具全部只读，外部修改必须 Human-in-the-loop。
- **理由**：安全第一，避免 Agent 越权破坏用户数据。

### ADR-0005 LLM / Embedding / 向量库 / DB 均走抽象接口
- **决策**：统一抽象层（Provider 接口），默认实现 DeepSeek(LLM) / 可插拔 Embedding / Qdrant / PostgreSQL。
- **理由**：便于替换供应商、便于离线测试、符合 v2.0「必须合理抽象」要求。

### ADR-0006 SDK 通过 HTTP 上报，不直连数据库
- **决策**：`sdk/agenttrace/` 通过 `POST /ingest/trace` HTTP 上报采集数据，后端 ingest 服务鉴权后写入 PostgreSQL。
- **理由**：符合五层架构（采集层只依赖服务接口层）；SDK 是外部 Agent 接入，不应持有数据库凭据；鉴权集中在服务端（`Project.api_key_hash`）。

### ADR-0007 SDK 鉴权用 sha256(api_key) + 常数时间比较
- **决策**：`Project.api_key_hash` 只存 sha256 哈希（不存明文），`secrets.compare_digest` 常数时间比较。
- **理由**：数据库泄露不可逆；避免时序侧信道；创建项目时一次性返回明文 Key。
